# Dynamic account selection

- **Status:** Implemented.
- **Supersedes:** None.

The direction of an inferred amount on an omitted-amount posting depends on
booking decisions that may not be known in advance, making it difficult to
specify the target account for a realized gain or loss statically.

This proposal lets an omitted-amount posting select its destination account from
booking-time facts. Selection rules can branch on debit/credit direction and,
for realized amounts from reduced lots, on the reduction context, source
account, and holding period.

## Background

When a posting omits its amount, Ledger infers it from the transaction's running
balance by posting the inverse of the balance accumulated so far for each
currency. This running balance includes postings generated by earlier costed or
priced postings in the transaction.

For example, reducing a costed position and receiving proceeds can leave either
a credit residual (a gain) or a debit residual (a loss) for the final income
posting:

```text
2026-11-01 * "Buy stock"
  Assets:Broker:Stock 10 ACME {{ 100 USD }}
  Assets:Broker:Cash  ; Inferred: -100 USD

2026-11-02 * "Sell stock"
  Assets:Broker:Stock -10 ACME {}
  Assets:Broker:Cash  120 USD
  Income:Broker:Capital-Gains  ; Inferred: -20 USD
```

Here `-20 USD` (a 20 USD credit) is inferred as a realized capital gain and
posted to `Income:Broker:Capital-Gains`. However, if the proceeds were `90 USD`,
the inferred amount would be `10 USD` (a 10 USD debit), which the user may want
to book to a separate loss account:

```text
2026-11-02 * "Sell stock"
  Assets:Broker:Stock -10 ACME {}
  Assets:Broker:Cash   90 USD
  Income:Broker:Capital-Gains:Losses  ; Inferred: 10 USD
```

While obvious in a single-lot sale, the outcome is hard to predict when multiple
lots and booking methods are involved. Users may also need to route short-term
and long-term capital gains to different accounts based on each reduced lot's
holding period.

## Objective

Allow users to specify account-selection rules evaluated against booking-time
facts, supporting debit/credit direction for balance residuals and per-lot
reduction context, source account, and holding period for realized amounts.

For example:

```text
2026-11-01 * "Buy stock"
  Assets:Broker:Stock 10 ACME {{ 100 USD }}
  Assets:Broker:Cash

2026-11-02 * "Sell stock"
  Assets:Broker:Stock -10 ACME {}
  Assets:Broker:Cash  120 USD
  choose account {
    when direction is debit: Income:Broker:Capital-Gains:Losses,
    when direction is credit and holding-period < 365d:
      Income:Broker:Capital-Gains:Short-Term,
    when direction is credit and holding-period >= 365d:
      Income:Broker:Capital-Gains:Long-Term
  }
```

## Requirements

### Core

1. **Preserve accounting invariants.** Dynamic account selection _MUST NOT_
   alter the total inferred amount or per-currency transaction balancing rules.
   The amounts offered for selection _MUST_ always conserve the transaction's
   running balance, and zero amounts _MUST NOT_ produce booked postings.
2. **Backwards compatibility.** Existing postings with a static account _MUST_
   retain their syntax and behavior.
3. **Bounded rule evaluation.** Selection conditions _MUST_ use a declarative,
   bounded expression grammar without arbitrary code execution. Invalid
   conditions, unsupported attributes, or unavailable booking facts _MUST_
   produce source-located errors.

### User

1. **Fact-based routing at the finest available granularity.** Users _MUST_ be
   able to select an account based on booking-time facts. Realized amounts from
   lot reductions _MUST_ be evaluated per reduced lot, exposing whether the
   amount comes from a reduction, its debit/credit direction, the reduced
   account, and the lot's holding period, so a single transaction can route
   realized portions to different accounts. All other inferred amounts _MUST_ be
   aggregated per currency and routed by debit/credit direction.
2. **Deterministic, composable matching.** Rules _MUST_ be evaluated in source
   order using first-match semantics, with an optional final fallback branch.
   Unmatched amounts _MUST_ remain available to subsequent omitted-amount
   postings in the same transaction.
3. **Selective account validation.** Only accounts selected for a nonzero amount
   _MUST_ be validated against account-reference, closed-account, and
   allowed-currency rules; unselected candidate accounts _MUST NOT_ be
   validated.
4. **Shared posting metadata.** A posting flag and metadata on a dynamic-account
   posting _MUST_ apply to every booked posting it emits.
5. **Reusable rules.** Users _MUST_ be able to define a named selection rule
   once and reference it across multiple postings.

## Proposal

We introduce a `choose account` posting form for omitted-amount postings:

```text
[flag] choose account {
  when <condition>: <account>
  [, when <condition>: <account>]...
  [, otherwise: <account>]
} [metadata]
```

For example:

```text
2026-11-01 * "Close position"
  Assets:Broker:Stock    -10 ACME {}
  Assets:Broker:Cash  10,000 USD
  choose account {
    when direction is debit: Income:Broker:Capital-Gains:Losses,
    otherwise: Income:Broker:Capital-Gains
  }
```

### Portion attribution and evaluation

`choose account` evaluates two kinds of candidate portions: per-lot **reduction
portions** and per-currency **aggregate residuals**.

1. **Reduction groups and proceeds.** A posting that reduces one or more costed
   lots opens a reduction group. Subsequent unannotated postings with explicit
   amounts contribute proceeds to the active group until another reduction, a
   cost- or price-annotated posting, an ordinary omitted-amount posting, or a
   `choose account` posting closes the group:
   - Multiple explicit amounts within a group are netted by currency (for
     example, gross sale proceeds and fees).
   - For each cost currency of the reduced lots, net proceeds are allocated
     proportionally by reduced unit quantity. Each reduced lot's realized
     portion is the inverse of (`allocated proceeds + cost basis`).
   - A reduction group with no explicit proceeds has zero proceeds.
   - Amounts posted before any reduction, generated by costed augmentations or
     price annotations, or denominated in currencies outside the reduced lots'
     cost basis are not attributed to the reduction group; they remain in the
     general running balance.

   ```text
   2026-11-01 * "Close positions"
     ; Group 1: -1 ACME, 98 USD net proceeds
     Assets:Broker:Stock   -1 ACME {}
     Assets:Broker:Cash   100 USD
     Assets:Broker:Cash    -2 USD ; Fees
     ; Group 2: -2 FOO, 149 USD net proceeds
     Assets:Broker:Stock   -2 FOO {}
     Assets:Broker:Cash   150 USD
     Assets:Broker:Cash    -1 USD ; Fees
     choose account { ... }
   ```

2. **Aggregate residuals.** When evaluating a `choose account` posting, Ledger
   computes one aggregate residual per currency equal to the inverse of the
   current running balance minus the sum of pending reduction portions in that
   currency.

3. **Available facts.** Each nonzero portion is evaluated against the rule
   clauses using its booking facts:
   - `context`: `reduction` for per-lot realized portions, or `aggregate` for
     per-currency balance residuals.
   - `direction`: `debit` (positive canonical amount) or `credit` (negative
     canonical amount).
   - `source-account` (reduction only): the account from which the lot was
     reduced.
   - `holding-period` (reduction only): elapsed days (`d`) between the lot's
     acquisition date and the transaction date.

   Evaluating `source-account` or `holding-period` against an `aggregate`
   portion is a booking error.

   For example, a single selector can route a worthless option expiration
   separately from the cash outlay for a new position:

   ```text
   2026-11-01 * "Carry-over position"
     Assets:Broker:Options -1 ACME-20261101-C-200 {}
     Assets:Broker:Options  1 ACME-20261108-C-200 { 100 USD }
     choose account {
       when context is reduction and direction is debit:
         Income:Capital-Gains:Losses,
       when context is reduction: Income:Capital-Gains,
       otherwise: Assets:Broker:Cash
     }
   ```

4. **Rule matching and chaining.** Clauses are evaluated in source order; the
   first matching `when` clause (or trailing `otherwise`) selects the target
   account. Zero-amount portions are skipped without emitting a posting or
   validating an account. Unmatched reduction portions remain pending for
   subsequent `choose account` postings, and unmatched aggregate residuals
   remain in the running balance:

   ```text
     choose account {
       when direction is credit and holding-period >= 365d:
         Income:Broker:Capital-Gains:Long-Term
     }
     choose account {
       when direction is credit:
         Income:Broker:Capital-Gains:Short-Term
     }
   ```

   An ordinary omitted-amount posting consumes the entire remaining balance and
   clears any pending reduction portions. As always, the transaction must
   balance in every currency after all postings are processed.

### Reusable named account rules

Users can define a named rule once with the `account-rule` directive and
reference it in postings:

```text
account-rule "broker-capital-gains" {
  when direction is debit: Income:Broker:Capital-Gains:Losses,
  when direction is credit and holding-period >= 365d:
    Income:Broker:Capital-Gains:Long-Term,
  when direction is credit and holding-period < 365d:
    Income:Broker:Capital-Gains:Short-Term
}

2026-11-01 * "Close position"
  Assets:Broker   -10 ACME {}
  Assets:Cash  10,000 USD
  choose account "broker-capital-gains"
```

Named rules are declarative definitions, not text macros. During loading, Ledger
validates that rule names are non-empty and unique, converts condition literals
to their runtime types, and stores definitions in a registry while preserving
named references on postings. During booking, Ledger verifies that referenced
rules exist, compiles each rule once, and evaluates it against the posting's
booking facts.

### Formal grammar

The following ABNF (using RFC 7405 case-sensitive `%s` literals) specifies the
new directive and posting forms. `RWS` and `OWS` denote required and optional
whitespace. Because the lexer discards whitespace (including newlines), clauses
in a rule block are comma-separated, with an optional trailing comma.

```abnf
account-rule-directive = %s"account-rule" RWS string RWS rule-block [OWS metadata]

account-choice-posting = [posting-flag RWS] account-choice [OWS metadata]
account-choice         = %s"choose" RWS %s"account" RWS
                         (rule-block / string)

rule-block             = "{" OWS when-clause
                         *(OWS "," OWS when-clause)
                         [OWS "," OWS otherwise-clause]
                         OWS ["," OWS] "}"

when-clause            = %s"when" RWS condition OWS ":" OWS account
otherwise-clause       = %s"otherwise" OWS ":" OWS account

condition              = or-expression
or-expression          = and-expression
                         *(RWS %s"or" RWS and-expression)
and-expression         = not-expression
                         *(RWS %s"and" RWS not-expression)
not-expression         = %s"not" RWS not-expression
                       / primary-expression
primary-expression     = comparison
                       / "(" OWS condition OWS ")"
comparison             = attribute RWS comparison-operator RWS literal
attribute              = identifier
comparison-operator    = %s"is" [RWS %s"not"]
                       / "==" / "!=" / "<" / "<=" / ">" / ">="
literal                = identifier
                       / existing-string-token
                       / existing-expression
                       / existing-date-token
                       / existing-amount
                       / existing-account-token
                       / existing-currency-token
                       / duration
duration               = existing-number-token OWS %s"d"
identifier             = LOWER *(LOWER / DIGIT / "_" / "-")

account                = existing-account-token
string                 = existing-string-token
posting-flag           = existing-posting-flag
metadata               = existing-metadata

RWS                    = 1*(SP / HTAB / CR / LF)
OWS                    = *(SP / HTAB / CR / LF)
```

Lexical and syntactic notes:

- `account-choice-posting` cannot have an explicit amount, cost specification,
  or price specification.
- `existing-*` rules reuse Ledger's existing lexer tokens and parser
  productions.
- The comparison operators `==`, `!=`, `<=`, `<`, `>=`, and `>` are new lexer
  tokens (matched longest-first).
- Logical precedence from highest to lowest is `not`, `and`, `or`, overridable
  with parentheses. Comparisons are not chainable. `is`/`==` test equality;
  `is not`/`!=` test inequality; `<`, `<=`, `>`, `>=` require compatible ordered
  types.
- `and`, `or`, `not`, and `is` are reserved contextually within conditions and
  cannot be used as attribute names or unquoted identifier literals. Directive
  and fact keywords (`choose`, `account-rule`, `when`, `otherwise`, `direction`,
  `context`, `source-account`, `holding-period`, `debit`, `credit`, `reduction`,
  `aggregate`) are also recognized contextually and are not globally reserved.
- The parser accepts any `identifier` as an attribute and any `literal` on the
  right-hand side; booking validates attribute names, literal types, and
  operator compatibility.

## Design decisions

### Use a rule block over typed booking facts

Expressing account selection as a rule block over typed booking facts
(`context`, `direction`, `source-account`, `holding-period`) provides a single,
extensible mechanism rather than special-purpose syntax for each scenario.

In particular, `direction` is always `debit` or `credit`, derived from the
canonical amount rather than the user-facing sign. Under alternative sign
conventions (such as `normal-balance-positive`) or per-account `normal-balance`
overrides, the written sign changes for presentation, but the underlying debit
or credit direction remains invariant.

#### Rejected alternative: Choose by the written sign

Routing on positive versus negative written signs would tie account selection to
the active `sign-convention` and the target account's `normal-balance` side,
potentially routing the same economic transaction to different accounts when
display conventions change.

#### Rejected alternative: Dedicated syntax per scenario (e.g., two-account postings)

A shorthand syntax such as `<debit-account> | <credit-account>` was considered:

```text
2026-11-01 * "Close position"
  Assets:Broker:Stock    -10 ACME {}
  Assets:Broker:Cash  10,000 USD
  Income:Broker:Capital-Gains:Losses | Income:Broker:Capital-Gains
```

While concise for simple gain/loss routing, it cannot express holding-period
thresholds or multi-lot routing, and adding dedicated syntax for each new
booking criterion would fragment the language.

### Preserve per-lot realization and aggregate other amounts

A single `choose account` form handles both per-lot realizations
(`context is reduction`) and ordinary balance residuals
(`context is aggregate`). Because the aggregate residual for a currency is
defined as the inverse running balance minus pending reduction portions in that
currency, lot portions and aggregate residuals always sum to the exact amount
needed to balance the transaction.

Evaluating each reduced lot independently ensures that lots with different
acquisition dates or gains and losses are routed accurately rather than netted
together before selection. Conversely, aggregating non-reduction amounts per
currency avoids fragile heuristics that would try to attribute ordinary cash
flows, costed augmentations, or price annotations to specific postings.

#### Rejected alternative: Explicit `by reduction` selector mode

A separate form such as `choose account by reduction` would force users to
declare context that booking already knows from the transaction structure, and
would prevent a single selector from routing both reduction portions and the
remaining balance residual via `context`.

### Route each currency and reduction group in source order

Booking tracks reduction groups in source order and allocates proceeds
independently per reduction group and cost currency. Closing an active reduction
group when encountering a subsequent reduction or a cost/price-annotated posting
prevents unrelated balancing effects from contaminating an earlier sale's
proceeds, while still allowing multiple cash postings (such as gross proceeds
and fees) to be netted within the same group.

Validating only the accounts actually selected for nonzero portions ensures that
unused branches (for example, a closed loss account on a profitable sale, or an
account with currency restrictions not triggered by the current portion) do not
cause false booking errors.

### Use ordered first-match evaluation and allow partial matching

Evaluating `when` clauses top-to-bottom with first-match semantics makes rule
precedence explicit and lets users write concise, overlapping conditions without
repeating negated predicates in every branch. Leaving unmatched portions pending
for later postings allows users to compose multiple specialized `choose account`
postings in sequence before a final catch-all or ordinary omitted-amount
posting.

#### Rejected alternative: Treat an unmatched portion as an error

Requiring every `choose account` posting to match all offered portions would
force every selector to include a catch-all branch, preventing sequential
filtering across multiple postings. Under the chosen design, any portion left
unconsumed at the end of the transaction still fails the standard transaction
balancing check.

#### Rejected alternative: Require mutually exclusive conditions

Requiring exactly one `when` clause to match each portion would turn overlapping
predicates into runtime errors and force users to write verbose, mutually
exclusive boolean expressions as conditions grow more complex.

### Preserve named rule references through loading

The loader validates `account-rule` syntax and uniqueness, but leaves named
references unresolved until booking.

#### Rejected alternative: Expand named rules during loading

Replacing each named reference with a copy of the rule AST during loading would
duplicate rule structures across loaded transactions and test snapshots, erase
the distinction between inline and named rules, and prevent booking from
compiling a named rule once and caching its evaluator across transactions.
